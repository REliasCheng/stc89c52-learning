## 读代码后，我能说清的几条线索

- 对照[数码管静态显示代码](../projects/02_数码管/src/course/03-数码管-静态显示/src/main.c)和[扩展板图](../hardware/schematics/extension-board/SCH_51教学扩展板V1.0_2024-05-30.pdf)，我把显示拆成位选和段码两件事：P1.3–P1.5 经过 74HC138 选位置，P0 送该位置要亮的段。再读动态工程，才需要考虑清 P0 消影与反复刷新。这是[目前的硬件理解](我的硬件理解.md)，实际位序、亮度还没上板确认。
- 比较[定时器初版](../projects/06_定时器/src/course/10-定时器/src/main.c)和[封装版](../projects/06_定时器/src/course/11-定时器封装/src/main.c)，前者的 `main()` 只初始化后空转，后者把 `LED_Blink` 注册为回调。查功能时要继续追到驱动和中断，而不能因为 `main()` 空着就以为没有动作。
- 整理 EEPROM 工程时，我沿 `main → Int_EEPROM → Dri_IIC` 追了一次调用。这里没有单独可下载的 I²C 工程，所以我没有凑出一个“已完成的 I²C 实验”。

这些读码结论都能指回原文件，构成已有实践的技术复盘；具体波形或运行数值仍需另有原始记录支持。工程习惯上，我把“源码可读、Build 出 HEX、下载成功、板上现象正确”分成四种不同证据，避免用一种代替另一种。

## 早前开发环境排障（未把日期硬填成实验进度）

- EIDE 调用的 Python 曾缺少 `serial` 模块；需要在**同一解释器**安装 `pyserial`，只在另一个 Python 里装包无效。
- CH340K 串口在不同连接中出现过 COM3/COM5；先核对设备管理器和硬件 ID，再决定上传端口，不能盲改配置。
- EIDE 的 `flash` 任务只是委派上传。遇到“无 HEX”时要先确认 Build 是否产出文件及 `build/Release/` 路径，再排查串口。

这些是此前环境检查中的真实问题，不代表本次仓库调整重新复现了全部故障。具体操作留在[常见问题](常见问题.md)。下一次记录应补：实验编号、日期、板卡版本、构建/烧录结果、照片或串口输出，以及失败后做过的修改。
