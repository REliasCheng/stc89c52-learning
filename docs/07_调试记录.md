# 调试记录与待验证问题

[首页](../README.md) · [FAQ](08_常见问题.md)

本页区分「此前环境中确实遇到」与「阅读源码发现的疑点」。仓库建立过程未接板、未烧录；下列源码疑点保持课程原样，尚不能写成硬件复现的故障。

## 已遇到的环境问题

| 情况 | 定位/处理 | 留意 |
| --- | --- | --- |
| `No module named serial` | 在 **EIDE 调用的同一个 Python** 解释器执行 `python -m pip install pyserial`，随后 `python -c "import serial; print(serial.__version__)"` 验证 | `serial` 模块来自 `pyserial` 包 |
| `COM3`/`COM5` 改变 | 设备管理器核对当前 CH340K 的端口与硬件 ID，更新上传端口 | 不凭猜测改成某个固定 COM |
| 无 HEX / 找错 HEX | 先检查 EIDE Build 是否成功，再看项目 `build/Release/` 或 Keil `Objects/` | `.vscode` 的 flash 任务只是委派 EIDE 上传 |
| 路径/工具链问题 | 核对 Keil C51、STC 设备头文件、EIDE 工程的绝对 include 路径与输出目录 | `Keil_C51` 配置仍依赖本机安装 |
| 串口有端口但无法烧录 | 核对当前端口占用、CH340K 驱动、STC89C52RC 型号、冷启动步骤、11.0592 MHz 和 12T | Python 可导入不代表设备连通 |

## 源码阅读发现，尚待复测

- `04-数码管-动态显示/src/main.c` 将 `u16` 写成 `unsigned char`，`Delay1ms(u16 count)` 的参数范围与名字不符。
- `14-串口-单字节命令/src/Dri/Dri_UART.c` 启用了 `ET1`，但未见对应 Timer1 ISR；接收函数也以非零字节判断“有数据”，无法区分收到 `0x00`。15 工程不再启用 ET1。
- `15-串口-多字节命令/src/Dri/Dri_UART.c` 对 16 字节接收缓冲未做长度边界处理；主程序接收数组的终止符也要核对。不要在不受控串口输入下依赖其稳定性。
- `18/19` 的 `Int_DS18B20.c` 在发出温度转换命令后立即重置并读暂存器，没有明确等待本次转换完成。
- `19-DS1302/src/main.c` 启动时调用 `SetDate` 写入示例初值，重复上电会重新设置时间；这是当前示例行为，不是可靠的持久 RTC 产品逻辑。
- `09` 的外部中断内包含延时消抖；`10` 的 ISR 函数命名 `Dir_Timer0_Handler` 与 `Dri_` 惯例不一致。两者都是原文件现状。

修复顺序建议：先在可复现板卡上记录预期/实际，再以单独提交改动，并在对应实验 README 更新「已验证」状态；不要把推测当成已经修好的问题。
