# 我的工程思考：先弄清资源，再追数据流

[首页](../README.md) · [工程结构](工程结构.md) · [硬件引脚](../hardware/引脚映射.md) · [调试记录](调试记录.md)

这些判断来自仓库内的课程实践、代码和教学板 V1.0 图纸。课程实现保持原样；这里写的是我怎样分析它们，以及从简单实验走向组合应用时需要守住什么边界。

## 一根 P0，不止一个外设

最早的[点灯代码](../projects/01_LED/src/course/00-点亮LED/main.c)直接拉低 P0.0。到了[数码管静态显示](../projects/02_数码管/src/course/03-数码管-静态显示/src/main.c)，P0 变成段码数据，P1.3–P1.5 通过 74HC138 选位；到[点阵](../projects/07_点阵/src/course/12-点阵LED/src/Int/Int_LEDMatrix.c)，P0 又参与一行像素的输出。P3.4/P3.5/P3.6 的使能决定当前谁在使用这组线。

这让我不再把 `P0 = ...` 当作完整的硬件描述。定位“灯没亮”或“显示错位”时，先画出**数据线 + 选通线 + 外设**，再看端口值；否则可能改了正确的段码，却忘了检查选中了哪个器件。[板级接线依据](../hardware/引脚映射.md)

## 定时器提供节拍，应用决定动作

[Timer0 初版](../projects/06_定时器/src/course/10-定时器/src/Dri/Dri_Timer0.c)在 ISR 内计数并直接翻 LED；[封装版](../projects/06_定时器/src/course/11-定时器封装/src/Dri/Dri_Timer0.c)维护回调表。此后点阵把扫描函数注册进去，[UART 多字节工程](../projects/08_UART/src/course/15-串口-多字节命令/src/Dri/Dri_UART.c)也注册空闲计数函数。它们复用同一类时间基准，却执行不同的应用任务。

我把这看作从“能用定时器”到“能分配时间资源”的变化：驱动负责重装和分发，应用负责显示刷新或帧结束判断。与此同时，中断回调会影响响应时间，不能把任意长的阻塞操作塞进去；[INT0 中的 10 ms 延时](../projects/05_外部中断/src/course/09-外部中断/src/main.c)正好提供了一个取舍例子。

## 总线动作与器件语义分层

在[EEPROM 工程](../projects/09_I2C与AT24C02/src/course/16-EEPROM/src/main.c)，`main` 操作的是一段要保存的图案；`Int_EEPROM` 处理控制字节、页边界和写入等待；`Dri_IIC` 处理起始、停止、位传输和 ACK。到了[OLED 工程](../projects/10_OLED/src/course/17-OLED/src/main.c)，底层仍是 P1.6/P1.7 的 I²C，器件接口却换成命令、数据和字模。

我从这两份工程理解到：协议线脚相同，不代表器件接口可以混成一个函数。排错时先判断卡在总线时序、器件地址/控制字节，还是应用传入的数据。对于 EEPROM，读回并显示图案只能说明程序经过了这条路径，不能代替逐字节校验。

## 综合应用先拆，再合

[DS1302 综合工程](../projects/12_DS1302/src/course/19-DS1302/src/main.c)一次调用 RTC、DS18B20 和 OLED：三线接口读日期，1-Wire 取温度，再通过 I²C 写到屏幕。看屏幕输出时，我先分清输入数据、格式化和显示传输三个阶段；单凭“屏上出现数字”不能确定时钟走时或温度精度。

这也是为什么[DS18B20 转换后立即读取](../projects/11_DS18B20/src/course/18-DS18B20/src/Int/Int_DS18B20.c)和[DS1302 启动时重设示例日期](../projects/12_DS1302/src/course/19-DS1302/src/main.c)要原样指出。它们不抹去组合应用的学习成果，但决定了我能怎样准确描述成果：这是多接口协同的课程实践，不是已经有保持时间与温度精度报告的成品仪表。

我的排查顺序最终固定为：**先确认板卡与线脚，再确认工程配置和构建产物，再沿驱动/接口/应用层追调用，最后用实际记录评价板上行为。** 已遇到的 `pyserial`、HEX 路径和 COM 口变化，正是把环境故障与应用 Bug 分开的实例。[实际排障入口](常见问题.md)
