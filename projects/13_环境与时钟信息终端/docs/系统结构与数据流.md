# 环境与时钟信息终端：系统结构与数据流

## 1. 应用边界

这个项目把 DS1302、DS18B20、OLED、AT24C02 和独立按键组合在一个应用中。`terminal_app.c` 只管理页面、事件、刷新节拍和配置状态；C51 适配层负责调用板级驱动。这个边界让同一套应用逻辑既能用 Windows GCC 的模拟平台测试，也能接入 STC89C52RC 工程。

![系统结构图](../../../assets/images/environment-clock-terminal-architecture.svg)

## 2. 模块职责

| 模块 | 文件/接口 | 职责 |
| --- | --- | --- |
| 应用核心 | `practice/core/terminal_app.c` | 页面切换、温度偏移、周期采样、配置脏标记 |
| 平台接口 | `TerminalPlatform` | 将 RTC、温度、配置和显示抽象成回调 |
| 板级入口 | `practice/c51/main.c` | 初始化外设、映射按键、绑定课程驱动 |
| 温度适配 | `Int_DS18B20_Safe.c` | 启动转换、等待 750 ms、读取暂存器 |
| 主机测试 | `practice/tests/test_terminal_app.c` | 使用 MockPlatform 验证状态与调用次数 |

## 3. 输入与状态变化

```text
SW1 → NEXT      → CLOCK → TEMPERATURE → SETTINGS → CLOCK
SW2 → PREVIOUS  → 反向切换页面
SW3 → ADJUST    → 仅在 SETTINGS 页循环调整 -5…+5 ℃偏移
SW4 → SAVE      → 仅在配置变脏时写入 AT24C02
```

页面变化与偏移调整只修改 `TerminalConfig`，不会在每次主循环中写 EEPROM。`config_dirty` 将“状态发生变化”和“用户确认保存”分开，减少非易失存储器无意义写入。

## 4. 周期数据流

主循环每 100 ms 调用一次 `terminal_app_tick()`。应用核心累计 10 个 tick 后调用 RTC 和温度回调，相当于每秒更新一次数据；显示回调仍可在状态变化后立即刷新。

```text
100 ms tick
   ↓ ×10
读取 DS1302 ─┐
读取 DS18B20 ├─→ 更新 TerminalApp 数据 → 按当前页面渲染 OLED
读取配置（仅初始化）┘
保存配置（仅 SAVE 事件）→ AT24C02
```

## 5. 三个驱动问题的处理

### RTC 启动策略

板级入口只调用 `Int_DS1302_Init()` 并读取当前时间，不在每次复位时写固定日期。真正的首次校时应作为独立操作，而不是藏在普通启动流程中。

### DS18B20 转换等待

安全接口在发送 `0x44` 后等待 750 ms，再重新复位并发送 `0xBE` 读取暂存器。当前实现优先保证数据时序清楚；进一步优化时可以拆成“启动转换”和“到期读取”两个非阻塞状态。

### EEPROM 写入策略

初始化时读取 3 字节配置：magic、页面、温度偏移。只有用户按下保存键且配置已变化时才写入，避免主循环反复擦写。

## 6. 可复现验证

主机端测试通过 MockPlatform 记录 RTC 读取、温度读取、保存和渲染次数，并验证页面切换、偏移调整、显式保存和十个 tick 后的周期采样。板端验证继续按项目 README 中的清单执行，测试记录应分别注明工具链构建与实机现象。
