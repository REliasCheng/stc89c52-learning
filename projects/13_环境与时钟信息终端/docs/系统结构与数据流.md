# 环境与时钟信息终端：系统结构与数据流

## 1. 应用边界

这个项目为 DS1302、DS18B20、OLED、AT24C02 和独立按键定义应用接口。`terminal_app.c` 管理页面、事件、刷新节拍和配置状态；C51 适配层调用未随当前仓库发布的板级驱动。因此可复现的是可移植核心的主机测试，不是 STC89C52RC 目标构建或板端运行。

![系统结构图](../../../assets/images/architecture/environment-clock-terminal-architecture.svg)

## 2. 模块职责

| 模块 | 文件/接口 | 职责 |
| --- | --- | --- |
| 应用核心 | `practice/core/terminal_app.c` | 页面切换、温度偏移、周期采样、配置脏标记 |
| 平台接口 | `TerminalPlatform` | 将 RTC、温度、配置和显示抽象成回调 |
| 板级入口 | `practice/c51/main.c` | 外设调用与按键映射；外部驱动缺失，未目标构建 |
| 温度适配 | `Int_DS18B20_Safe.c` | 启动转换、等待 750 ms、读取暂存器 |
| 主机测试 | `practice/tests/test_terminal_app.c` | 使用 Fake Platform 验证正常、失败和恢复状态 |

## 3. 输入与状态变化

```text
SW1 → NEXT      → CLOCK → TEMPERATURE → SETTINGS → CLOCK
SW2 → PREVIOUS  → 反向切换页面
SW3 → ADJUST    → 仅在 SETTINGS 页循环调整 -5…+5 ℃偏移
SW4 → SAVE      → 仅在配置变脏时写入 AT24C02
```

页面变化与偏移调整只修改 `TerminalConfig`，不会在每次主循环中写 EEPROM。`config_dirty` 将“状态发生变化”和“用户确认保存”分开，减少非易失存储器无意义写入。

## 4. 周期数据流

设计中的主循环每 100 ms 调用一次 `terminal_app_tick()`。应用核心累计 10 个 tick 后调用 RTC 和温度回调；此节拍在主机测试中验证，板端时间精度未验证。显示回调也可在状态变化后立即刷新。

```text
100 ms tick
   ↓ ×10
读取 DS1302 ─┐
读取 DS18B20 ├─→ 成功后提交数据，失败保留上次有效值 → 按当前页面渲染
读取配置（仅初始化）┘
保存配置（仅 SAVE 事件）→ AT24C02
```

## 5. 三个驱动问题的处理

### RTC 启动策略

板级入口只调用 `Int_DS1302_Init()` 并读取当前时间，不在每次复位时写固定日期。真正的首次校时应作为独立操作，而不是藏在普通启动流程中。

### DS18B20 转换等待

安全接口在发送 `0x44` 后等待 750 ms，再重新复位并发送 `0xBE` 读取暂存器。当前实现优先保证数据时序清楚；进一步优化时可以拆成“启动转换”和“到期读取”两个非阻塞状态。

### EEPROM 写入策略

初始化时读取 3 字节配置：magic、页面、温度偏移。失败或无效配置采用确定的默认值。只有用户按下保存键且配置已变化时才尝试写入；C51 适配层写后读回比较，失败则保留脏标记。读回一致不证明 EEPROM 断电持久性。

## 6. 可复现验证

从仓库根目录运行 `python scripts/run_host_tests.py --compiler gcc`。Fake Platform 记录调用次数并注入 RTC、温度和保存失败，验证首次失败、上次有效值、恢复、页面切换和采样节拍。板端验证仍是待执行清单，测试记录须分别注明主机构建、C51 构建和实机现象。
